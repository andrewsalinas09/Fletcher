## Q-05 · Test protocols and statistics design — **Largely resolved 2026-08-23 → ADR-0012; residuals open**
**Shipped (ADR-0012):** both protocols (ABX one-sided exact binomial; preference two-sided, `preferredA`, never "correct" — TB-15 closed); sequential = Wald SPRT (H1 p=0.75, α=β=0.05, cap 40, declared-before-first-vote, server-decided so nothing leaks — satisfies (e)); fixed-vs-adaptive front-and-center in the NEW TEST rail (d); replication = "Run again" re-runs exact chains + material + stop rule (f); hidable stats + reveal provenance (a, TB-24) unchanged; labeled replay carries clip provenance per trial (b); the Lab is the finder with tag:/genre:/note: search and battery assembly (c); per-tag success breakdowns computed from provenance with a ≥8-trial floor (TB-10).
**Still open:** replication flagging ("conclusive but not reproduced" markers), per-headphone/per-preset-pair history dimensions, ear-training/gamification, preference sequential design (deliberately rejected for now — optional stopping inflates preference strength).
Late additions from Lab-home review: **(d) Protocol controls are prominent, not buried** — trial count customizable front-and-center; an "until statistically conclusive" adaptive mode with a Cancel (it may never converge). **(e) Sequential honesty**: the adaptive mode must use proper sequential statistics (checking after every trial inflates false positives — SPRT or alpha-spending corrected thresholds, not naive p&lt;0.05 per look), and the UI carries a plain professional note explaining that repeated looks raise the odds of a fluke "difference." **(f) Replication is first-class**: from any result, "run it again with the same N" — a conclusive result you can't reproduce gets flagged as such in the record. **(g) Layout note: Begin button right-aligned.**
New settled requirements from the user: **(a) Live stats are hidable-by-default during a session** — the user may reveal them mid-test, but the UI states in professional language that viewing interim results can bias sequential testing, and the session record notes when stats were viewed (provenance, TB-24). **(b) Labeled replay is mandatory**: every session stores the exact played sequence — trial order, X assignments, clips, matched levels — so the user can replay the whole session afterwards *with labels revealed* ("trial 7, X was B — listen again"). A test you can't relive is a test you can't learn from. **(c) The Lab is the retrieval surface**: Clip Studio annotates richly; the Lab's job is finding and searching exactly the material you want and assembling custom batteries from the database.
Two distinct test types are now in scope: **discrimination** (ABX — has a correct answer; binomial p-value) and **preference** (blind A/B vote — no correct answer; preference proportion vs. 50% null, needs its own stats treatment, TB-15). Design: trial counts fixed vs. sequential; what's reported; per-clip/per-band breakdowns from the clip battery (Q-11); history per user / per headphone / per preset pair; ear-training/gamification. Guard against misleading small-N (TB-10).

## Q-12 · The Fingerprint Lab: capture, library, bridging — **Open (vision clarified 2026-08-22)**
Its own tab, visibly its own setup. **Capture:** a guided "capture headphone fingerprint" flow — sweeps + multiple reseatings per headphone, measured at *your* ears, so each fingerprint is the coupled HpTF∘ear response (HpTF and HRTF are not separable here, and don't need to be: within one person's library the ear factor cancels when comparing two fingerprints). **Library:** fingerprints accumulate per headphone; exportable/importable, so reviewers (headphones.com, The Headphone Show) can publish libraries. **Bridging:** given a shared headphone between two libraries, transfer other fingerprints across — (X_on_reviewer − shared_on_reviewer) applied to shared_on_you ≈ X for you — enabling at-home virtual auditioning of "basically any headphone," trustworthy mainly below ~5–6 kHz. Open: sweep method details, reseating protocol and acceptance stats (TB-14), regularization/boost caps (TB-16), and what "statistically identical" means as a per-band tolerance.
**Rulings 2026-08-23 (user):** ① The UMIK-2/iMM-6 are NOT in-ear mics (none owned yet) — the dev path is **any USB mic + free-air sweeps**, standing in for ear-coupled capture: the machinery (sweep+capture sync, reseating stats, cal files) is identical, only the coupling differs. ② Matching verification is a **loop, not a single re-measurement**: match → blind "can you hear it" test → refine — the GAN framing (the EQ match is the generator, the human ABX is the discriminator; iterate until the human can't tell). The Lab's trial engine is that discriminator, already built. ③ (see Q-15) bridging uses every shared headphone, not one anchor.

## Q-16 · Loudness-compensation volume anchoring — **Open (calibration flow settled 2026-08-23)**

## Q-19 · Mic-free hearing profile: procedure design — **Resolved 2026-08-23 → ADR-0013; v1 shipped**
Resolved by research-grounded design (the ISO 226 measurement literature — Takeshima/Suzuki RMLSP lineage): direct-to-anchor comparisons (500 Hz octave), timed 2I-2AFC pairs (800/300/50 ms), dual bracketing 1-up-1-down PSE staircases (4→2→1 dB, 6 min-step reversals, cap 40) on a normalized-RMS level axis, exclusive-only playback, censored rails, catch-trial reliability (lapse + order), interleaved scheduling, journal-replay resume, per-headphone MASTER averages. All constants + records in ADR-0013 and the frozen stats tests. **Still open for v2:** RMLSP as the estimator, refinement bands (subdivide where the curve moves fast), left/right ear split, replay caps if journals show abuse, ISO 226 exact table for the context overlay (v1 uses an approximate shape).
**The path to target-hood (user asked "why can't this be an EQ target?", 2026-08-24 — answer recorded):** the raw curve never is (it's mostly normal biology all music already assumes; headphone×ear×hearing are fused; valid at one loudness only). But the **deviation from a population baseline measured the same way** is a candidate signal once (a) a same-procedure baseline exists, (b) mic fingerprints separate headphone from ears, and (c) any derived correction is validated the Fletcher way — a level-matched blind preference/ABX, never auto-applied. Even true deviations may not want correcting (the brain calibrates to its own ears) — which is precisely what the preference protocol measures. This interpretation layer is the TB-23-compliant future, not v1.
Raised 2026-08-22. The user's sketch: match loudness of adjacent noise bands (0–5k vs 5k–10k), recursively subdivide (0–2.5k vs 2.5k–5k, …), overlapping bands to isolate narrow regions, all statistics-driven yes/no answers. Design questions: (a) adaptive procedure — standard psychoacoustics is 2AFC with a transformed staircase (e.g. 2-down-1-up → 70.7% convergence), which beats fixed-step yes/no on trials-to-convergence; (b) band spacing — log/ERB (critical bands) rather than linear halves; (c) overlapping-band isolation propagates error — direct narrow-band trials with adaptive tracking may beat subtraction; (d) **target semantics**: equal-loudness across bands is NOT flat-preference — normal hearing has the ISO 226 contour shape built in, so the profile must be interpreted *relative to population-average contours*, not flattened absolutely (TB-23); (e) level anchoring — results are only valid at the test loudness (Fletcher–Munson again), so the session must fix and record its level; (f) fatigue management — session chunking, resume, convergence display.

## Q-20 · Pop-out windows with synced state — **v1 shipped (history + difference graph); platform law learned**
The history tree is the first pop-out: shared component, main window owns truth, satellites send commands over targeted events (`emitTo`), live-synced both ways. The **difference graph** is the second (2026-08-23): `?view=diff`, fed by `diff-sync` — main resolves the last-touched inspector's compare against the live tree on every change, so with the default compare (current vs parent) the window continuously shows "what did my last gesture change" while sculpting; the satellite computes curves itself via the stateless `chain_curves`. No keyboard needs → no OS-shortcut work. **Platform law (2026-08-23, hard-won; refined same day):** runtime-created WebView2 windows do NOT deliver *page-level* DOM keyboard events — capture-phase listeners, `window`/`document` keydown, focus grabbing: all dead ends. Any pop-out needing app shortcuts uses **focus-scoped OS shortcuts** (register on window focus, unregister on blur/close, fire in Rust, forward as events). This is the pattern for Clip Studio's J/K/L, the Lab's A/B/X, and every future room. **Refinement (user-verified live on the satellite ⚙ menu's number fields):** focused `<input>`/`<textarea>` elements DO receive typed keys normally — the black hole is document-level handlers, not the widgets. So form editing works in satellites; only shortcut-style keys need the OS route.
**Platform law #2 (2026-08-23, bit twice):** Tauri v2 capabilities are per-window-*label* — a runtime-created window whose label isn't covered in `capabilities/default.json` renders fine but has NO IPC: `listen`/`emit`/`invoke` all silently dead ("waiting for the main window…" forever). Fixed as a class: `"windows": ["*"]`. Never enumerate labels there again.
**Dev law (2026-08-23, corrected same day):** vite fast-refresh does NOT re-run `[]`-effects — so any long-lived listener (Tauri events, window keydown) that captures app closures directly keeps executing the code *from when the window mounted*, forever. Symptom: satellite→main commands run stale behavior (or hit a dispatch case that didn't exist yet and silently no-op) while the main-window path runs current code — parity quietly breaks. Class fix in place: every such listener is a permanent **trampoline** dispatching through a ref that's refreshed each render (`busRef`/`keyRef` in App.tsx) — register the callback once, swap only the ref body. Any NEW long-lived listener must follow this pattern.
**Pop-outs compose hub-and-spoke, not nested:** any satellite can request any other window (⇱ in the popped-out history opens the diff window) — but the request always routes through main (`hist-cmd: popdiff`), which owns creation. Feels like infinite nesting; avoids orphaned chains when an intermediate window closes.
Raised 2026-08-22 during design: any tab can pop out into its own OS window (curve editor on one monitor, Listening Lab on another), and everything updates together in real time. Architecturally cheap for us: the Rust core is already the single source of truth and windows are views (ADR-0001/0005) — Tauri supports multiple windows natively; core broadcasts state changes to every window. Open: which tabs earn pop-out first, window-state persistence, and how the A/B bar behaves across windows (in every window? only the focused one?).

## Q-25 · Advanced signal composition — **Open (design direction proposed)**
User request 2026-08-23 (right after the generator v1 shipped): *"I also want a way to make really advanced stuff too."* The v1 generator makes single primitives; advanced material means combining them. The recipe is already JSON on the track row (`signal_params`, deterministic seed = id), so the natural growth path keeps provenance intact by making `SigSpec` recursive:
- **`mix`** — sum N layers, each a spec with its own level (pink bed at −24 + 3 kHz sine probe at −18; a "cocktail-party" of band-noises).
- **`seq`** — segments in time, each a spec with its own length (2 s silence → sweep → burst train), with per-segment edge fades.
- **Modulators** as optional fields on any layer: AM (rate/depth — tremolo, burst gating), FM for sines, later envelopes.
- **UI in two tiers**: a "Layers" builder in the modal (rows = specs, add/remove, per-row level + solo-preview) for the common cases, and an **"Edit recipe as text"** escape hatch — the JSON itself in a textarea with validate + live preview — as the true power path (cheap to ship, covers everything the engine can do before the builder UI catches up).
Everything stays deterministic and capped at −12 dBFS total after summing (TB-20: the cap applies to the MIX, not per-layer, or four layers could stack to clipping).
**Ruled 2026-08-23 (user) and shipped same day:** `seq` is NOT built here — sequencing = clips of signals in a battery (the Lab owns it; the inspector's "Add to battery" placeholder was removed accordingly). `mix` ✓ (one level of layers, master–detail editor, decorrelated per-layer seeds, cap binds the sum), modulators ✓ (tremolo on anything, vibrato on tonal kinds), text tier ✓ (the `{ }` editor in the generator modal: recipe JSON with validate-on-apply via `signal_validate`). **The recipe JSON is the future API/MCP surface** (user: "exposed via API / MCP server eventually") — treat `SigSpec` as a public schema from here on: additive changes only, never rename or repurpose fields.
Remaining open: nested mixes (one level only today), envelopes, and the eventual API/MCP exposure itself.
